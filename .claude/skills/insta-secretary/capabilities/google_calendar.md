# Googleカレンダー連携 — 予定の読み取り

## これは何の道具か

Googleカレンダーに入っている予定を、秘書がプログラムから読み取れるようにする窓口（API＝サービス同士をつなぐ窓口）。主に `recipes/morning_report.md`（朝のひとこと報告）で「今日の予定」を取ってくるために使う。

- できるのは**読み取りだけ**。予定の追加・変更・削除は一切しない
- 利用は**無料**。カレンダーを読むことでお金がかかることはない（`safety.md` ③のとおり、これも先に伝える）
- 一度セットアップすれば、以後は本人の操作なしで予定を読める

始める前に本人へこう説明する:「Googleに『このプログラムに予定を見せてもいいよ』と許可をもらう手続きです。最初だけ10〜15分の画面操作があり、そのあとは自動です。読み取り専用なので、予定が書き換わる心配はありません」

## 準備の手順

画面の操作は本人にやってもらう。秘書は**1ステップずつ**案内し、できたことを確認してから次へ進む。Google Cloud Consoleの画面の文言は時期によって少し変わるので、見つからないときは近い言葉のボタンを探してもらう。

1. **Google Cloud Consoleを開く**
   - ブラウザで https://console.cloud.google.com/ を開き、普段使っているGoogleアカウントでログインしてもらう
   - 初めての場合は利用規約への同意画面が出る。内容を確認して同意してもらう（無料の範囲で使うので、ここで課金は発生しない）
2. **プロジェクトを作る**（プロジェクト＝この連携の設定をまとめて入れておく箱）
   - 画面上部のプロジェクト名（または「プロジェクトの選択」）をクリック →「新しいプロジェクト」
   - 名前は分かりやすいものに（例: `ai-hisho`）→「作成」
   - 作成後、画面上部の表示がそのプロジェクト名に切り替わっているか確認する
3. **Google Calendar APIを有効にする**
   - 左上の三本線メニュー →「APIとサービス」→「ライブラリ」
   - 検索窓に「Google Calendar API」と入力し、出てきたカードをクリック →「有効にする」
4. **OAuth同意画面を設定する**（OAuth＝本人としてログインして「許可します」と渡す仕組み）
   - 「APIとサービス」→「OAuth同意画面」（新しい画面では「Google Auth Platform」という名前のこともある）
   - User Type（利用者の種類）は「外部」を選ぶ
   - アプリ名（例: `ai-hisho`）と本人のメールアドレスを入力して保存する
5. **公開状態は「テスト」のままにして、テストユーザーに本人を登録する**
   - 公開申請はしない。「テスト」のままで個人利用には十分
   - 「テストユーザー」（新しい画面では「対象」ページ）で追加ボタンを押し、**本人のGmailアドレスを登録**する
   - これを忘れると初回の承認で「アクセス権がありません」と弾かれるので、必ずここで確認する
6. **OAuthクライアントIDを作る**（クライアントID＝このプログラムの身分証）
   - 「APIとサービス」→「認証情報」→「認証情報を作成」→「OAuthクライアントID」
   - アプリケーションの種類は**「デスクトップアプリ」**を選ぶ。名前はそのままでよい →「作成」
7. **JSONファイルをダウンロードして、決めた場所へ置く**
   - 作成完了の画面（または認証情報一覧のダウンロードボタン）から**JSONをダウンロード**してもらう
   - あらかじめ本人と決めた保管場所（例: `~/secretary/credentials/google_calendar.json`）へ移動する
   - 置き場所は `safety.md` ④のとおり1か所に固定し、おしごとカード（`templates/oshigoto_card.md`）に記録する
8. **初回実行して、ブラウザで承認してもらう**
   - 秘書が用意した読み取りプログラムを初めて動かすと、ブラウザが自動で開く
   - 「このアプリはGoogleで確認されていません」という警告が出るが、**自分で作ったアプリなので問題ない**と伝え、「続行」→ カレンダー読み取りへの同意、と進んでもらう
9. **トークンの保存を確認して完了**（トークン＝次回から使える入館証のファイル）
   - 承認が済むと入館証ファイルが自動で保存され、以後はブラウザなしで予定を読めるようになる
   - 仕上げに「今日の予定を1件読んでみる」まで一緒に確認してから完了とする

## 使い方のポイント

- 権限（スコープ＝許可の範囲）は**読み取り専用の `calendar.readonly` だけ**を要求する。書き込みの権限は、本人に「ついでに付けて」と言われても付けない。読むことしかできない状態そのものが、本人の安心材料になる
- morning_reportでは「今日の0時〜24時の予定」を取り、開始時刻の早い順に並べて報告に載せる
- 仕事用・家族用などカレンダーが複数あるときは、どれを読むかを最初に本人に選んでもらう（質問はひとつずつ、A/B/C形式で）
- 本人に説明するときは、専門用語に必ず一言の言い換えを添える（例:「認証＝あなた本人だとGoogleに確認してもらうこと」）

## 気をつけること

- **公開状態が「テスト」のままだと、入館証（トークン）が約7日で期限切れになることがある。** 壊れたのではなく、もう一度ブラウザで承認すれば元どおり動く。朝の報告で「予定が読めませんでした」となったら、まずこれを疑う。本人には「7日ごとの再承認はGoogleの仕様で、あなたのせいではありません」と伝える
- ダウンロードしたJSONと入館証ファイルは、チャットに貼らない・共有フォルダに置かない・スクリーンショットに写さない（`safety.md` ④）
- 予定の中身（人の名前・案件名）は本人の大事な個人情報。報告に使う以外の用途には使わず、外部のサービスへ送らない
- この連携を常駐の仕組み（毎朝の自動実行など）に組み込むときは、`capabilities/patrol.md` の見回りをセットにし、失敗の記録は `_patrol/` に残す
- うまくいかないときは、上の手順の何番で止まったかと、画面に出ている文言をそのまま教えてもらう。3回直しても動かなければ、正直にそう伝えて別のやり方を相談する（`instructions.md` の方針どおり）
